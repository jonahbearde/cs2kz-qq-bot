# Spec: CS2KZ QQ 小贴士机器人

Status: ready-for-agent

## Problem Statement

维护者经营一个 CS2KZ 主题的 QQ 群，希望群成员能持续、被动地接触到简短的 CS2KZ 知识（身法技巧为主），而不是靠维护者手动转发或群成员自己翻教程。维护者不懂 QQ 机器人的部署与配置，需要一份从零开始的中文操作手册。机器人不能有任何额外功能（不聊天、不响应指令），以免干扰群内正常交流。

## Solution

一个运行在维护者 Ubuntu 服务器上的单进程 Python 机器人，以官方 QQ 机器人平台（个人主体）身份接入，驻留在单一目标群中。在每天 09:00–24:00（北京时间）的发送窗口内，每 30 分钟向目标群发送一条维护者手写的 Tip（纯文本、一两句话、无前缀），按洗牌袋轮播，发完一整轮重新洗牌。贴士存于一行一条的 tips.txt，改动即热加载。发送失败重试一次后跳过，宕机不补发，重启记住轮播进度。配套一份保姆级手册，覆盖注册实名 → 创建机器人 → 拉群开权限 → 服务器部署 → 测试群验收 → 切换正式群 → 日常维护与排错。

## User Stories

1. As a 群成员, I want 白天每 30 分钟在群里看到一条一两句话的 CS2KZ 小贴士, so that 我能碎片化地积累身法知识而不用自己翻教程。
2. As a 群成员, I want 机器人在 00:00–09:00 保持沉默, so that 我的夜间休息不被消息打扰。
3. As a 群成员, I want 同一轮轮播内不出现重复的贴士, so that 内容保持新鲜而不是复读机。
4. As a 群成员, I want 贴士是手机 QQ 直接可读的纯文本, so that 我不会遇到 Markdown/卡片渲染不出来的问题。
5. As a 群成员, I want 机器人永不回复聊天、不响应任何指令, so that 群内正常交流不被打扰。
6. As a 群成员, I want 每条贴士都经过维护者人工审核, so that 我不会被错误的身法细节误导。
7. As a 维护者, I want 自己在 tips.txt 里一行一条地手写贴士, so that 内容准确性完全由我掌控，不依赖任何生成服务。
8. As a 维护者, I want 在 tips.txt 里用空行和 # 注释组织内容, so that 我可以分组和备注而不影响发送。
9. As a 维护者, I want 在服务器上增删改贴士后无需重启服务即可生效, so that 日常维护只是编辑文件保存。
10. As a 维护者, I want 贴士列表为空时机器人静默跳过并记录警告, so that 误操作不会让机器人崩溃或乱发。
11. As a 维护者, I want 轮播顺序是洗牌的, so that 群成员无法预测下一条，体验不像固定广播。
12. As a 维护者, I want 机器人重启后记住已发进度, so that 重启不会从头再来造成重复刷屏。
13. As a 维护者, I want 增删贴士后轮播自动重新洗牌, so that 新贴士立即进入轮播、删除的贴士不再出现。
14. As a 维护者, I want 发送时刻对齐整点/半点, so that 节奏可预测、日志易核对。
15. As a 维护者, I want 窗口中途启动的机器人等到下一个对齐时刻再发, so that 重启不会造成突发额外消息。
16. As a 维护者, I want 宕机期间错过的贴士不补发, so that 服务恢复时群里不会瞬间涌出几十条消息。
17. As a 维护者, I want 发送失败后 30 秒重试一次、再失败就跳过等下一时刻, so that 偶发网络抖动不丢贴士，持续故障也不形成重试风暴。
18. As a 维护者, I want 所有发送与失败都写入日志文件, so that 出问题时我能事后追查。
19. As a 维护者, I want 凭据与配置全部放在 .env, so that 密钥不进仓库、改配置不用改代码。
20. As a 维护者, I want 调度固定按北京时间, so that 服务器时区是 UTC 也不会导致发送窗口漂移。
21. As a 维护者, I want 通过配置修改发送间隔与发送窗口, so that 日后调整节奏不需要改代码。
22. As a 维护者, I want 先在自己创建的测试群里验证全流程, so that 调试过程不拿正式群刷屏。
23. As a 维护者, I want 按手册步骤从测试群切换到正式群（@ 机器人捕获新 group_openid、改配置、重启）, so that 切换不需要我理解代码。
24. As a 维护者, I want 机器人即使身在多个群也只向配置的目标群发送, so that 测试群与正式群不会串线。
25. As a 维护者, I want 机器人在被 @ 时把该群的 group_openid 醒目地记入日志, so that 我不用查任何 API 文档就能完成配置。
26. As a 维护者, I want 一份从零开始的中文操作手册（注册、实名、创建、拉群、开权限、部署、验收、日常维护、排错）, so that 完全不懂部署的我也能照着跑起来。
27. As a 维护者, I want 服务开机自启、崩溃自动拉起, so that 服务器重启后不用我手动干预。
28. As a 维护者, I want AppSecret 只存在于服务器的 .env 中, so that 仓库公开也不会泄露凭据。
29. As a 维护者, I want 手册明确提示 AppSecret 离开创建页面即不可见, so that 我在创建时就会妥善保存而不是事后重置。

## Implementation Decisions

- **接入路线**：官方 QQ 机器人平台、个人主体（见 ADR 0001）。前提：维护者是目标群群主（已确认）。注册需姓名+身份证+手机号实名及人脸识别。个人主体机器人由创建者通过最新版手机 QQ 拉入自己任群主/管理员的群；群主须开启「机器人主动在群聊内发言」权限。新版管理端下管理员自有群无需沙箱、无需公开上架。
- **运行形态**：Ubuntu 服务器（Python 未预装，手册含 apt 安装步骤，要求 ≥3.8）上的单进程 Python 服务，venv 隔离依赖，systemd 管理（开机自启 + 崩溃自动重启）。不用 Docker。
- **SDK 与连接**：官方 qq-botpy（import botpy），Intents 开启 public_messages；WebSocket 出站连接，无需公网 IP/域名/Webhook。发送用 post_group_message（msg_type=0 纯文本、不带 msg_id 即主动推送）。
- **目标群标识**：group_openid 是"每 bot × 每群"的平台标识，不是 QQ 群号。机器人被 @ 时从 GROUP_AT_MESSAGE_CREATE 事件捕获并醒目写入日志，由维护者抄入 .env。机器人不回复任何消息，捕获仅为被动日志。切换目标群 = 在新群 @ 一次 → 改 .env → 重启。
- **配置**：全部经 .env 提供——AppID、AppSecret、目标群 group_openid、发送间隔（默认 30 分钟）、发送窗口起止（默认 09:00–24:00）。时区硬编码 Asia/Shanghai，与服务器时区无关。.env 不入仓库。
- **调度语义**：发送时刻对齐墙钟的间隔边界（30 分钟即 :00/:30）；窗口内首个时刻 09:00、末个 23:30，默认每天 30 条。窗口中途启动等待下一个对齐时刻，不立即发。错过的时刻不补发。
- **轮播**：洗牌袋——整份 Tip List 洗牌后逐条发送，一轮内不重复，发完重新洗牌。轮播状态（洗牌顺序 + 游标）持久化到本地状态文件，重启续发；状态文件损坏则重建。Tip List 增删后重新洗牌。
- **贴士文件**：tips.txt 一行一条 Tip，空行与 # 开头行忽略。每个调度时刻检测文件修改时间，变化则热加载并重新洗牌，无需重启。文件缺失或为空：跳过发送、记警告、进程继续运行。
- **失败策略**：发送异常 30 秒后重试一次，再失败跳过等下一时刻；全部写日志文件（带轮转），不做告警。
- **消息形态**：纯文本、无前缀。官方群 Markdown 需模板权限，不使用。
- **交付物**：机器人代码、tips.txt 示例文件（3–5 条标注为示例的条目，供维护者替换）、中文操作手册（注册 → 创建 → 拉群开权限 → 部署 → 测试群验收 → 切换正式群 → 日常维护 → 排错）、systemd 单元与安装说明。
- **术语**：全程使用 CONTEXT.md 词汇（Tip、Tip List、Send Window、Rotation、Target Group）。

## Testing Decisions

- **单一测试缝（seam）**：决策核心——"给定当前时刻、Tip List、轮播状态与配置，是否发送、发送哪条"。时钟与发送动作均为可注入替身（fake clock + fake sender），贴士与状态用真实临时文件。所有自动化测试只打这一个缝，断言外部可观察行为（什么时刻发了什么内容），不断言内部结构。
- **覆盖行为**：窗口边界（08:59 沉默 / 09:00 发送 / 23:30 末条 / 24:00 沉默）；时刻对齐；窗口中途启动等待；洗牌袋一轮内无重复且全覆盖；列表变更触发重新洗牌与热加载；状态跨重启存续；状态损坏重建；长间隔后不补发；失败重试一次后跳过；空列表/缺失文件静默加警告。
- **QQ 适配层**（botpy 接线、.env 装载、@ 事件捕获日志）保持极薄，不做单元测试，按手册验收清单在测试群人工验证：@ 捕获 openid → 收到主动推送 → 改 tips.txt 热生效 → 重启续发。
- **测试框架**：pytest。仓库为绿地项目，无既有测试先例；本缝的测试即为后续先例。

## Out of Scope

- LLM 或任何运行时内容生成；贴士全部由维护者手写。
- 多目标群同时发送、按用户定向发送。
- 任何交互：回复、指令、@ 响应（捕获 openid 的被动日志除外）。
- Markdown、ARK、 embed、富媒体消息。
- 告警、监控面板、Web UI。
- Docker 部署、频道/单聊场景。
- 宕机补发、消息撤回。
- DRY_RUN 开关（维护者选择用独立测试群代替）。

## Further Notes

- 默认节奏的数学：30 分钟 × 15 小时窗口 = 每天 30 条。Tip List 少于 30 条时洗牌袋一天转多圈，同一条当天会重现；维护者已知悉，欲每条每日仅现一次需 ≥30 条。
- 平台政策有变动先例（2025-04 砍主动推送、2026-06 恢复）。QQ 适配层与决策核心隔离，若路线再变，更换成本集中在薄适配层。
- 手册撰写时须以当前管理端与手机 QQ 实际 UI 为准逐步核对（个人主体拉群路径、权限开关位置可能随版本变化）；关键步骤设验证检查点。
- 残余风险：个人主体机器人在非沙箱自有群的主动推送能力以平台实际表现为准，测试群验收即为该风险的验证手段。
